Documentação de Planejamento

a) Descrição do projeto, objetivos e requisitos

Descrição. A TaskFlow API é uma API REST para gerenciamento de tarefas (to-do list), permitindo criar, organizar e acompanhar tarefas por status (a fazer, em andamento, concluída) e por prioridade (baixa, média, alta).

Objetivos. Praticar um fluxo DevOps completo, da integração contínua ao provisionamento de infraestrutura como código, entregando uma API estável, testada automaticamente e com ambiente reproduzível via containers.

Requisitos funcionais.

  • CRUD de tarefas e de usuários.
  • Autenticação via JWT.
  • Filtros de listagem por status e prioridade.

Requisitos não funcionais.

  • Cobertura de testes automatizados.
  • Pipeline de CI executado a cada push e pull request.
  • Infraestrutura provisionada de forma automatizada via Terraform.

b) Plano de Integração Contínua

Ferramenta: GitHub Actions.   Gatilho: cada push e cada pull request aberta contra a branch main.

Etapas do pipeline:

  • Checkout do código.
  • Instalação das dependências com npm ci.
  • Lint com ESLint.
  • Execução dos testes automatizados com Jest e geração do relatório de cobertura.
  • Build da aplicação e da imagem Docker.

Critério de sucesso: o pipeline só é aprovado se lint, testes e build passarem sem erros. Falhas bloqueiam o merge da pull request (branch protection na main).

Pipeline de Integração Contínua (CI)

a) Repositório de código

Repositório criado no GitHub com estrutura organizada em pastas (src, test, infra e .github/workflows), README com instruções de execução, .gitignore, .gitattributes e template de pull request. A branch main tem proteção configurada exigindo pull request e checks de CI aprovados antes do merge.

Link do repositório: https://github.com/PatriciaSSRS/taskflow-ap

b) Pipeline de CI com GitHub Actions

Pipeline implementado em .github/workflows/ci.yml, disparado a cada push e pull request contra a main. O job build-and-test executa checkout, npm ci, lint com ESLint e os testes com Jest (com relatório de cobertura) contra um serviço PostgreSQL 16; o relatório de cobertura é publicado como artefato. O job docker-build faz o build da imagem Docker da aplicação. O merge só é liberado se todos os checks passarem.

Workflow: .github/workflows/ci.yml

Scripts de Infraestrutura como Código

a) Provisionamento com Terraform

Scripts Terraform (pasta infra/) que provisionam na AWS toda a infraestrutura necessária para rodar a API:

  • network.tf — VPC, Internet Gateway, subnet pública e duas subnets privadas (o RDS exige duas zonas de disponibilidade), tabela de rotas.
  • security_groups.tf — SG da aplicação liberando apenas 22, 80 e 443; SG do banco liberando 5432 somente a partir do SG da aplicação.
  • ec2.tf + user_data.sh — instância EC2 t3.micro, instalação do Docker e execução do container da API; Elastic IP.
  • rds.tf — instância RDS PostgreSQL db.t3.micro em subnet group privado.
  • variables.tf, outputs.tf, terraform.tfvars.example — parametrização e saídas (IP público e endpoint do RDS).

O estado do Terraform não é versionado (pode conter a senha do RDS); o infra/README.md documenta a migração para um backend remoto S3 + DynamoDB.

Link (pasta infra/): github.com/PatriciaSSRS/taskflow-ap/tree/main/infra

4

Testes Automatizados

Testes escritos com Jest e Supertest, separados em dois projetos: unit (utilitários de JWT, hash de senha e schemas de validação, sem I/O) e integration (fluxo completo da API — autenticação, usuários e tarefas — contra um PostgreSQL real). A aplicação é organizada em camadas routes → controllers → services → repositories, o que mantém as regras de negócio isoladas e testáveis.

Os testes rodam localmente com npm test e são integrados ao pipeline de CI: o job build-and-test executa npm run test:coverage a cada push e pull request, usando um container de serviço postgres:16-alpine e o banco taskflow_test. Uma falha de teste reprova o pipeline e bloqueia o merge.
